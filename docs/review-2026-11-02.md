## Assessment

The architecture is appropriate for this app. Keep the boundaries:

- `LooperCore`: preallocated C processing, bounded single-producer command queue, atomic telemetry. Capture happens before the backing/drum mix; live guitar is not software-monitored.
- `LooperAudioUnit` / `AudioEngineHost`: one shared graph, with platform-specific I/O and a dedicated drummer gain stage. Preserve the rule that Pop Drummer state is restored **after** attachment/render preparation.
- `JamCore`: chart parsing, library transformation and field-aware merges; exact pre-edit backups and coordinated writes are useful protections.
- `AM4RemoteKit`: self-contained local package, resource bundles, original protocol regressions, one app-owned MIDI session. Frequent MIDI updates stay inside the remote view; closing it does not tear down the audio engine or an in-flight verified edit.

The UI isolation and cached chart measurements already address the large update/layout churn described in `performance-validation.md`. I would improve the async edges below before a broad refactor or DSP optimization.

## Findings, in priority order

### 1. P2 — a stale Play request can autoplay a newly selected track

**Location:** `Sources/MacLooper/AudioEngineHost.swift:282`, especially the suspension at 284 and playback at 296.

`playFile` checks/captures the file session before `await waitForConfiguration()`, then operates on mutable host/player state without checking that session again. Selecting B while a Play for A waits replaces the host's file and session. A's continuation then calls `schedule`, which uses the **current B**, and starts it even though selecting a file should not autoplay. A graph rebuild introduces another suspension requiring the same protection.

**Confirmed:** an isolated test held configuration, requested Play(A), loaded B, released configuration, and observed B's playing flag become `true`. The graph used AVAudioEngine **offline** mode and synthetic silent files; no hardware playback was started.

**Fix direction:** validate session and transport intent after each suspension, including graph rebuilds. Use a command/request generation so Stop/Pause can invalidate a pending Play even when the selected file's session has not changed. Keep completion callbacks scoped to the existing `fileGeneration`. Avoid letting stale error cleanup disrupt a newer operation.

**Regression acceptance:** held-configuration Play(A) → select B must leave B paused; Play(A) → Stop/Pause must stay stopped/paused; replacing a track during graph setup must not autoplay it or surface an old track's error in the new selection.

### 2. P2 — switching library folders during a read can strand the old library

**Location:** `Sources/MacLooper/SongLibraryModel.swift:52` and `:79`.

`setFolder` increments the revision and schedules a refresh. If an earlier refresh is already reading, the new refresh returns at the `reading` guard. The old refresh later rejects its outdated result, but does not schedule a read of the newly selected folder. `folderURL` can point to New while the displayed library still comes from Old, until another refresh happens.

**Confirmed:** a synthetic Old/New library test held the library I/O actor queue, started the Old read, selected New, allowed its refresh task to run, then released Old. The model ended with folder New and song title Old.

**Fix direction:** coalesce refresh requests into a single flight that drains the latest requested revision/folder after the current read finishes. Carry the folder snapshot/revision through *all* asynchronous steps, including backing-link loading. Respect the editor/save guard. Keep any last-good-library fallback clearly associated with its actual source rather than presenting it as the newly chosen library.

**Regression acceptance:** switch folders while loading; switch twice; switch to a malformed/missing file; return to foreground during a read. The latest valid folder must eventually load, and old backing links/selection must not be treated as belonging to the new folder.

### 3. P2 — optional drummer loading gates unrelated audio startup

**Location:** `Sources/MacLooper/AudioEngineHost.swift:130–137`; `Sources/MacLooper/PopDrummerModel.swift:57` and `:96`.

Every graph rebuild awaits `drums.prepare()`, including guitar/backing-only startup. Missing-plugin discovery retries for about three seconds; instantiation has a fifteen-second timeout. Thus an optional missing/unresponsive drummer can delay otherwise usable guitar/backing audio. Failed discovery is retried on later rebuilds. This is a code-path finding; missing-plugin startup latency was **not** measured on this machine.

**Fix direction:** separate optional instrument discovery from the critical audio-route startup path, with explicit in-flight configuration ownership rather than repeated wait/sleep checks. Cache an unavailable result until an intentional retry or component-list change. Preserve captured loops, transport and prepared-state restoration when attaching/reconnecting the plugin. Test absent, slow and failed plugins, not just the installed happy path.

### 4. P3 — closing Amp during an operation can leave its old page selected for polling

**Location:** `Packages/AM4RemoteKit/Sources/AM4RemoteKit/AM4Connection.swift:402`; dismissal in `AM4RemoteSession.swift:15`.

The outer Remote Close is intentionally available during a verified edit. Amp editor disappearance asks `showAmpPage(nil)` to clear the polling page, but that function rejects **all** calls while `isApplyingGain`/`isNavigating` is true. Hidden polling is paused correctly; when Remote is reopened on its main screen, the stale Amp page can still be queried every refresh. The effect-page close path already treats clearing differently. This is a code-path finding, not a hardware reproduction.

**Fix direction:** allow clearing the page subscription during an operation without canceling its command or verification. Opening/switching pages should remain guarded. Add a lifecycle regression covering Close during an edit, operation completion, and reopening to the main screen.

Also consider eliminating the now-hidden USB playback-level read and legacy one-Gain compatibility read from normal refreshes when no consumer needs them. First count MIDI requests per visible page; retain the context reads and independent read-back checks that protect edits.

### Isolated C-core timing

Compiled the repository's unmodified `LooperCore.c` with `clang -O3`; rendered 100,000 synthetic 32-frame calls per condition at 48 kHz. No audio device, plugin, file decoding or UI was involved. Wall-clock measurements include timer overhead and normal process scheduling.

| Condition | Median | p99 |
| --- | ---: | ---: |
| Empty | 0.167 µs | 0.250 µs |
| Armed, below threshold | 0.167 µs | 0.209 µs |
| Arm + trigger, including pre-roll | 0.625 µs | 0.709 µs |
| Playing | 0.167 µs | 0.541 µs |

A 32/48k quantum is approximately 666.7 µs. These typical samples suggest the C core is not the first optimization target. **This is not a realtime deadline or whole-app benchmark:** the largest wall-clock outlier was 4.760 ms during playing, which can include OS preemption on this ordinary test thread. It does not establish actual device dropouts or attribute that entire delay to DSP. The existing Instruments results also compare different interaction windows and should retain their stated caveat.

For future performance comparisons, use the same chart, audio file, plugin state, route, quantum and interaction script before/after. Measure idle and active AM4 views separately; record main-thread CPU, render deadline misses, graph rebuild latency and memory over a longer soak. Avoid broad DSP changes without a controlled profile.

## Next AM4 milestone: explicit preset Save

The imported editor changes the working buffer. It has **no permanent Save implementation**. Carry forward the existing successful Type/Library/channel/parameter handshake behavior, including linked Amp/Cab normalization.

1. Passively capture the actual desktop AM4-Edit **Save current preset** operation on the user's device: request, acknowledgement/error replies and stored-state confirmation. Capture in-place Save separately from Save As. Do not guess an opcode from another Fractal model.
2. Implement Save as a serialized transaction in `AM4RemoteKit`, sharing the existing exclusion with edits/navigation/library transfers. Bind it to the intended location and current connection/session; reject a stale target. Disable duplicate saves while pending. Keep audio ownership in Mac Jams.
3. Use an explicit Save action. Dirty/saved status must follow the relevant preset and connection; “Verified on AM4” currently proves a working-buffer edit, **not persistence**. Prefer a firmware dirty/read status if one is available. Do not clear dirty state merely because a transport echo arrived.
4. Verify against independent persistent state where the protocol permits. A matching preset name alone does not prove edited parameter values were stored. Handle a lost response as an uncertain outcome; avoid blindly replaying a permanent operation.
5. On a user-chosen test preset, verify edits survive a deliberate navigate-away/back or reconnect. Test edits to multiple channels/scenes, interrupted USB, rejected/timeout responses, and closing Remote during Save. Obtain the user's intended destination before any Save As/overwrite test. Do not automatically reload a preset and discard its working edits just to test persistence.

After that, useful follow-ups are an explicit iPad background/interruption policy with lifecycle tests, durable recovery of unsaved chart drafts, and iCloud conflict-version handling. The current read/latest/field merge is valuable local protection; it is not a complete resolution mechanism for independently edited offline iCloud versions. Add explicit conflict detection/recovery before claiming full cross-device synchronization guarantees.

For fully self-contained simulator development, bring the optional MIDI helper launcher/entry point into this repo; its conditional server source is present, but the helper tool itself remains in the old checkout. Physical Mac/iPad direct MIDI does not depend on that helper.
